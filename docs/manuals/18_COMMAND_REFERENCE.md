## All Commands by Category

### 🎯 Strategic Planning (HITL)

#### `analyze`
Generate tactical attack plan from discovered endpoints.

```bash
Usage:
> analyze

Description:
Analyzes all discovered endpoints and generates attack scenarios with
confidence scores. Populates ActionBuffer (view with list-plan). Uses
tactical planning algorithm to combine endpoints, loot, traffic patterns
and operator context.

When to use:
- After running 'map' to discover endpoints
- Before executing attacks
- When ready to plan a coordinated attack

Output:
F5 PLAN tab populates with tactical actions

Example:
> target https://api.example.com
> map
> analyze
> list-plan (view generated actions)
```

#### `list-plan`
Display all pending tactical actions.

```bash
Usage:
> list-plan

Description:
Shows all actions generated by 'analyze' that are PENDING or COMPLETE.
Displays ID, Type (BOLA/BFLA/SSRF), Target endpoint, Payload, Confidence
score (HIGH/MEDIUM/LOW), and Status (PENDING/SUCCESS/FAILED/DROPPED).

When to use:
- After running 'analyze'
- To review actions before commit
- To check execution results after commit

Output:
List of actions in tactical feed (F1)
Also visible in F5 PLAN tab as table

Example:
> list-plan
[08:30:00] ACTION 1: BOLA /api/users [HIGH] [PENDING]
[08:30:01] ACTION 2: BFLA /api/admin [MEDIUM] [PENDING]
```

#### `edit <id> <new_payload>`
Override payload for a specific action.

```bash
Usage:
> edit <action_id> <new_payload>

Parameters:
- <action_id>: Action ID (from list-plan)
- <new_payload>: New payload to use

Description:
Allows you to manually edit a tactical action's payload before execution.
Useful for testing specific values or bypassing AI-generated suggestions.

When to use:
- When you want to test a specific endpoint
- To override AI suggestions
- When you know the target better

Example:
> analyze
> list-plan
[Shows ACTION 1: BOLA /api/users/[id] ...]
> edit 1 /api/users/999
[08:30:05] ACTION 1 payload updated to: /api/users/999
```

#### `drop <id>`
Mark an action as DROPPED (won't execute on commit).

```bash
Usage:
> drop <action_id>

Parameters:
- <action_id>: Action ID to drop (from list-plan)

Description:
Marks a tactical action as DROPPED so it won't execute during 'commit'.
Useful for excluding noisy or false-positive actions. Can be undone by
re-running 'analyze'.

When to use:
- To skip noisy attack vectors
- To avoid testing certain endpoints
- To focus on specific vulnerabilities

Example:
> list-plan
[Shows ACTION 2: BFLA /api/admin [LOW] PENDING...]
> drop 2
[08:30:10] ACTION 2 marked as DROPPED
```

#### `commit`
Execute all PENDING tactical actions.

```bash
Usage:
> commit

Description:
Executes all actions with PENDING status. Each action runs in parallel
with real-time feedback in F5 (PLAN) tab and F6 (NEURO) tab. Updates
status to SUCCESS or FAILED based on results. Captures findings and
loot automatically.

When to use:
- After 'analyze' and reviewing actions
- Ready to actually run the attacks
- Want all results in one batch

Output:
- F5: Action status updates in real-time
- F1: Execution logs for each action
- F3: Loot table populated with findings
- DB: Persistent storage of results

Timing:
Each action typically takes 5-30 seconds depending on complexity

Example:
> analyze
> list-plan
> commit
[08:30:20] EXEC: Starting tactical action execution...
[08:30:25] EXEC: ACTION_1 BOLA /api/users - SUCCESS (3 objects)
[08:30:30] EXEC: ACTION_2 BFLA /api/admin - FAILED (no priv escalation)
```

#### `remediate <type>`
Generate middleware patches for vulnerabilities.

```bash
Usage:
> remediate <vulnerability_type>

Parameters:
- <vulnerability_type>: bola, bfla, bopla, ssrf, etc

Description:
Generates middleware code patches to fix identified vulnerabilities.
Outputs code snippets for common frameworks (Express, FastAPI, Django).
Currently generates basic templates (Sprint 16 will enhance).

When to use:
- After identifying vulnerabilities
- To generate fix suggestions
- For compliance documentation

Example:
> remediate bola
[Template for BOLA prevention middleware]
```

### 🔍 Reconnaissance & Discovery

#### `target <url>`
Set global scope URL.

```bash
Usage:
> target <url>

Parameters:
- <url>: Full URL (https://api.example.com)

Description:
Sets the global target URL for all reconnaissance and exploitation
modules. Updates pipeline panel on left side of dashboard.

When to use:
- At the start of any penetration test
- When switching targets
- Before any recon module

Example:
> target https://api.example.com
[08:30:00] TARGET: https://api.example.com
```

#### `map [url]`
Full automatic reconnaissance (spider + swagger + scraper).

```bash
Usage:
> map
> map https://custom-url.com (optional override)

Description:
Runs full attack surface mapping:
1. Spider: Crawl all accessible endpoints
2. Swagger: Check for OpenAPI/Swagger specs
3. Scrape: Extract endpoints from JavaScript

Discovers hidden endpoints, parameters, API versions. Results shown
in F2 MAP tab as table with timestamp, source, endpoint, metadata.

When to use:
- Start of any test (discover what you're attacking)
- After deploying new API versions
- To get baseline of attack surface

Duration: 30 seconds to 5 minutes depending on site size

Example:
> target https://api.example.com
> map
[08:30:05] DISCOVER: Starting mapping...
[08:30:15] SPIDER: Found 23 endpoints
[08:30:25] SWAGGER: Found spec at /api/v1/swagger.json
[08:30:35] SCRAPE: Found 5 more endpoints in JS
```

#### `swagger <url>`
Parse OpenAPI/Swagger specifications.

```bash
Usage:
> swagger <url>
> swagger https://api.example.com/swagger.json

Description:
Manually load OpenAPI 3.0 or Swagger 2.0 specifications. Extracts all
defined endpoints, parameters, and methods. Imports into database for
analysis.

When to use:
- If 'map' doesn't find Swagger automatically
- When testing API with explicit spec documentation
- To speed up reconnaissance

Example:
> swagger https://api.example.com/openapi.yaml
[08:30:40] SWAGGER: Parsed 34 endpoints from spec
```

#### `scrape <url>`
Extract API endpoints from JavaScript.

```bash
Usage:
> scrape <url>
> scrape https://api.example.com/app.js

Description:
Analyzes JavaScript bundles for hidden API endpoints. Uses regex patterns
to find fetch(), axios(), or XMLHttpRequest calls. Useful for SPAs and
modern applications that dynamically call APIs.

When to use:
- For single-page applications (React, Vue, Angular)
- When traditional spidering doesn't find all endpoints
- To discover internal/admin endpoints

Example:
> scrape https://api.example.com/js/main.js
[08:30:50] SCRAPE: Found endpoints:
[08:30:50]   /api/v1/users
[08:30:50]   /api/v1/admin/users
[08:30:50]   /api/v1/billing/invoices
```

#### `mine <url>`
Brute-force hidden query parameters.

```bash
Usage:
> mine <url>
> mine https://api.example.com/api/users

Description:
Tests common parameter names (debug, admin, test, version, etc) to
discover hidden functionality. Brute-forces GET/POST parameters to find
testing/debug endpoints.

When to use:
- After discovering endpoints with 'map'
- To find debug/test parameters
- To discover version-specific endpoints

Duration: 1-3 minutes per endpoint

Example:
> mine https://api.example.com/api/users
[08:31:00] MINE: Testing common parameters...
[08:31:05] FOUND: ?debug=true (200)
[08:31:10] FOUND: ?admin=1 (200)
[08:31:15] FOUND: ?version=v2 (200)
```

#### `sessions`
Display and manage authentication tokens.

```bash
Usage:
> sessions
> sessions list
> sessions add <name> <token>
> sessions use <name>

Description:
Manages authentication context (cookies, JWT, API keys). Allows storing
multiple auth tokens for different users/roles. Automatically injects
into subsequent requests for privilege escalation testing.

When to use:
- After obtaining authentication tokens
- To test privilege escalation (switching users)
- To test with multiple auth contexts

Example:
> sessions list
[08:31:20] SESSION 1: attacker_user - eyJ0...
[08:31:20] SESSION 2: admin_user - eyJ0...
> sessions use 2
[08:31:25] Using admin_user session
```

### ⚔️ Exploitation

#### `bola <url>`
Test BOLA (Broken Object Level Authorization).

```bash
Usage:
> bola <url>
> bola https://api.example.com/api/users/[id]

Description:
Tests ID enumeration and object access control bypass. Tries sequential
IDs (1,2,3...) and random IDs to see if you can access objects you
shouldn't. Captures any returned data.

OWASP: Broken Object Level Authorization (API1:2019)

When to use:
- On any endpoint with ID parameter (/users/{id})
- Where authorization might be weak
- To find sensitive user data

Results in F3 LOOT if objects are captured

Example:
> bola https://api.example.com/api/users/[id]
[08:31:30] BOLA: Testing /api/users/1
[08:31:35] BOLA: Found 15 accessible users!
[08:31:40] CAPTURED: user@example.com, user2@domain.com, ...
```

#### `bfla <url>`
Test BFLA (Broken Function Level Authorization).

```bash
Usage:
> bfla <url>
> bfla https://api.example.com/api/admin/reset

Description:
Tests privilege escalation by attempting to access admin/elevated
functions without proper authorization. Tries with different tokens
(user, admin, service account). Tests role-based access control bypass.

OWASP: Broken Function Level Authorization (API2:2019)

When to use:
- On admin/elevated endpoints (/admin/*, /management/*)
- With limited-privilege user tokens
- To test RBAC implementation

Example:
> bfla https://api.example.com/api/admin/reset
[08:31:45] BFLA: Attempting privilege escalation...
[08:31:50] BFLA: Admin endpoint accessible! [200]
[08:31:55] BFLA: PRIVILEGE ESCALATION SUCCESSFUL
```

#### `bopla <url>`
Test BOPLA (Broken Object Property Level Authorization).

```bash
Usage:
> bopla <url>
> bopla https://api.example.com/api/users

Description:
Tests mass assignment vulnerability by injecting extra properties into
requests. Tries to set properties that should be restricted (admin flag,
balance, role, etc). Checks if server accepts and processes them.

OWASP: Broken Object Property Level Authorization (API3:2019)

When to use:
- On POST/PUT endpoints that accept object data
- When creating or updating user profiles
- To test property-level authorization

Example:
> bopla https://api.example.com/api/users
[08:32:00] BOPLA: Injecting restricted properties...
[08:32:05] BOPLA: Injected 'admin=true' - ACCEPTED [200]
[08:32:10] BOPLA: Injected 'balance=9999' - ACCEPTED [200]
```

#### `ssrf <url>`
Test SSRF (Server-Side Request Forgery).

```bash
Usage:
> ssrf <url>
> ssrf https://api.example.com/api/fetch

Description:
Tests Server-Side Request Forgery by attempting to access internal
services (metadata endpoints like 169.254.169.254 for AWS, localhost
services, etc). Checks if server makes internal requests on your behalf.

OWASP: Server-Side Request Forgery (API5:2019)

When to use:
- On endpoints that fetch external URLs (fetch, proxy, webhook)
- To access internal cloud metadata
- To test internal network access

Example:
> ssrf https://api.example.com/api/fetch
[08:32:15] SSRF: Testing internal metadata access...
[08:32:20] SSRF: Attempting 169.254.169.254
[08:32:25] SSRF: FOUND AWS credentials! [200]
[08:32:30] CAPTURED: AWS_ACCESS_KEY_ID=AKIA...
```

#### `exhaust <url>`
Test resource exhaustion (DoS).

```bash
Usage:
> exhaust <url>
> exhaust https://api.example.com/api/data

Description:
Tests rate limiting and resource exhaustion by sending rapid requests
with large pagination/data requests. Finds rate limits, response times,
and resource usage patterns.

When to use:
- To identify rate limiting thresholds
- To test pagination limits
- To understand resource constraints

Example:
> exhaust https://api.example.com/api/data
[08:32:35] EXHAUST: Testing rate limits...
[08:32:40] EXHAUST: 100 requests/sec: OK
[08:32:45] EXHAUST: 500 requests/sec: RATE LIMITED
[08:32:50] EXHAUST: Rate limit: 400 requests/sec
```

#### `audit <url>`
Configuration security audit.

```bash
Usage:
> audit <url>
> audit https://api.example.com

Description:
Checks security headers (HSTS, CSP, X-Frame-Options), SSL/TLS version,
certificate validity, CORS policy, and other configuration issues.

When to use:
- General security audit
- Compliance checks
- Configuration review

Example:
> audit https://api.example.com
[08:32:55] AUDIT: HSTS header: PRESENT
[08:33:00] AUDIT: CORS: Allow-All (⚠️  RISKY)
[08:33:05] AUDIT: SSL: TLS 1.3 ✓
```

#### `probe <url>`
Test webhook injection vulnerabilities.

```bash
Usage:
> probe <url>

Description:
Tests webhooks and 3rd-party integrations for unsafe consumption.
Attempts to inject payloads that might be reflected back or processed
by downstream systems.

When to use:
- On endpoints that support webhooks
- With integrations (Slack, Teams, PagerDuty)
- For testing chain vulnerabilities

Example:
> probe https://api.example.com/webhooks
[08:33:10] PROBE: Testing webhook injection...
[08:33:15] PROBE: Payload reflection: YES (⚠️  XSS)
```

#### `flow <action>`
Manage and execute attack chains.

```bash
Usage:
> flow list                 (show saved chains)
> flow clear                (clear current chain)
> flow run                  (execute chain sequentially)
> flow race                 (execute chain with timing randomization)

Description:
Orchestrates multi-step attack chains. Combine multiple modules into
sequences that execute with dependencies and timing controls.

When to use:
- Complex attack scenarios
- Sequential exploitation (first escalate, then exfiltrate)
- Stress testing with coordinated attacks

Example:
> flow list
[08:33:20] Chain 1: Discover -> BOLA -> Exfiltrate
> flow run
[08:33:25] Step 1: map
[08:33:35] Step 2: bola /api/users/[id]
[08:33:45] Step 3: loot list
```

### 🧠 AI & Neural Engine

#### `neuro on|off`
Enable/disable the Neural Engine.

```bash
Usage:
> neuro on
> neuro off

Description:
Toggles AI-driven payload mutation and generation. When ON, the neural
engine analyzes responses and generates optimized payloads using LLM.
Requires API key configured (see Configuration).

When to use:
- When you have LLM API access
- For more sophisticated payload generation
- To learn from response patterns

Requirements:
- NEURO_API_KEY environment variable set
- API credits/account active

Example:
> neuro on
[08:33:30] NEURO: Neural Engine activated
[08:33:30] NEURO: Connected to Groq (llama-3.1-8b)
```

#### `neuro-gen <n>`
Generate n high-entropy payloads.

```bash
Usage:
> neuro-gen 5
> neuro-gen 10

Parameters:
- <n>: Number of payloads to generate

Description:
Uses neural engine to generate n alternative payloads for current
attack. Useful for testing multiple mutation strategies or bypassing
WAF rules.

When to use:
- WAF is blocking some payloads
- Want to test multiple approaches
- Need diverse payload set

Example:
> neuro-gen 5
[08:33:35] NEURO: Generating 5 payloads...
[08:33:40] NEURO: Payload 1: [mutation 1]
[08:33:40] NEURO: Payload 2: [mutation 2]
[08:33:40] NEURO: Payload 3: [mutation 3]
...
```

#### `test-neuro`
Connectivity and latency test.

```bash
Usage:
> test-neuro

Description:
Tests connection to neural engine API and measures latency. Useful for
verifying API access and understanding response times.

Example:
> test-neuro
[08:33:45] NEURO: Testing connection to Groq...
[08:33:50] NEURO: Connected ✓
[08:33:50] NEURO: Latency: 245ms
[08:33:50] NEURO: Model: llama-3.1-8b
```

#### `ask <prompt>`
Direct LLM query.

```bash
Usage:
> ask "How would you bypass this auth scheme?"
> ask "Generate 10 SQLi payloads for MySQL"

Description:
Send arbitrary prompt to LLM for analysis, generation, or advice.
Useful for research or getting AI insights on security topics.

Example:
> ask "Generate 5 payloads for BOLA bypass"
[08:33:55] NEURO: Generating payloads...
[08:34:00] NEURO: Payload 1: /api/users/1/../../admin
[08:34:00] NEURO: Payload 2: /api/users/9999999999
...
```

### 🚀 Infrastructure & Configuration

#### `proxy <host:port>`
Set upstream proxy.

```bash
Usage:
> proxy localhost:8080
> proxy burp.internal:8080

Description:
Routes all HTTP traffic through upstream proxy. Useful for inspection,
request modification, or integration with Burp Suite/other tools.

Example:
> proxy localhost:8080
[08:34:05] PROXY: Set to localhost:8080
[08:34:05] PIPELINE & STATUS - PROXY (STAT): localhost:8080
```

#### `proxies load`
Load proxy list for rotation.

```bash
Usage:
> proxies load

Description:
Loads rotating proxy list for anonymity/evasion. Rotates between proxies
for each request to evade detection.

File format: `proxies.txt` with one proxy per line
```

#### `init_db`
Create/initialize database.

```bash
Usage:
> init_db

Description:
Creates SQLite database with all tables (Endpoints, Findings, Loot,
Sessions). Run this on first launch.

Example:
> init_db
[08:34:10] DATABASE: SQLite initialized at ~/.vaportrace/vaportrace.db
```

#### `seed_db`
Insert test/demo data.

```bash
Usage:
> seed_db

Description:
Populates database with sample data for testing. Useful for demos or
testing report generation without running actual attacks.
```

#### `reset_db`
Clear all data.

```bash
Usage:
> reset_db

Description:
⚠️  WARNING: Deletes all mission data from database. Cannot be undone!
Use with caution.
```

#### `report`
Generate findings report.

```bash
Usage:
> report
> report html              (alternative format)

Description:
Exports all findings to Markdown/PDF report. Includes vulnerabilities,
loot captured, confidence scores, and remediation tips.

Output: ./reports/VAPORTRACE_PEN_TEST_[timestamp].md

Example:
> report
[08:34:15] REPORT: Generating findings report...
[08:34:20] REPORT: Saved to ./reports/VAPORTRACE_PEN_TEST_20260208_0834.md
```

### 🛠️ Utilities

#### `tasks`
Show active engine status.

```bash
Usage:
> tasks

Description:
Lists all active threads/goroutines:
- Context Aggregator (tactical planning)
- Neural Engine (AI mutations)
- Interceptor (MITM)
- Proxy Pool (request routing)

Example:
> tasks
[08:34:25] TASKS: Active engines
[08:34:25] - Context Aggregator: RUNNING (23 goroutines)
[08:34:25] - Neural Engine: RUNNING (1 goroutine)
[08:34:25] - Interceptor: RUNNING (pending: 0)
```

#### `loot`
Manage captured secrets.

```bash
Usage:
> loot
> loot list                (show all captured loot)
> loot export              (export to file)

Description:
Views captured secrets (emails, tokens, credentials, API keys).
Also accessible via F3 tab in dashboard.

Example:
> loot list
[08:34:30] LOOT: 23 items captured
[08:34:30] EMAIL: user@example.com (from /api/users)
[08:34:30] JWT: eyJ0... (from /api/profile)
[08:34:30] AWS_KEY: AKIA... (from /metadata)
```

#### `clear`
Clear tactical feed.

```bash
Usage:
> clear

Description:
Wipes F1 (LOGS) tab. Useful for cleaning up after experiments.
```

#### `usage`
Show all commands with descriptions.

```bash
Usage:
> usage

Description:
Displays organized list of all 40+ commands grouped by category with
short descriptions.
```

#### `help <command>`
Detailed help for specific command.

```bash
Usage:
> help analyze
> help bola
> help keys           (see all hotkeys)

Description:
Shows comprehensive help with examples for specified command.
```

#### `exit`
Graceful shutdown.

```bash
Usage:
> exit

Description:
Terminates VaporTrace cleanly, saving session state and closing all
connections.
```
